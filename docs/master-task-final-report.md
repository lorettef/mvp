Закрыты следующие реальные разрывы:

   Теперь сервисы `insight_service` и `plan_generation_service` подставляют реальный профиль компании

3. **Пункт 24 (редактирование конфигурации)** — не было UI для изменения Geo/Industry/Business Model

4. **Пункты 6+7 (выбор метрик)** — шаг «Метрики» онбординга был read-only. Сделан интерактивным

Дополнительно исправлен UX-дефект: в списке компаний и шапке компании отображались сырые slug-и
(`saas`, `subscription`) вместо человекочитаемых подписей — теперь подписи берутся из каталога.

## 2. Architecture

**Текущая архитектура** (не изменилась структурно):

```
Браузер (React 18 + TS + shadcn/ui + Tailwind + Recharts)
   │ HTTPS / REST
   ▼
Nginx (reverse proxy)
   ▼
FastAPI 0.115 (Python 3.12, SQLAlchemy 2 async)
   │               │
   ▼               ▼
PostgreSQL 15   DeepSeek / GigaChat API (AI)
(SQLite для dev/тестов)
```

**Что изменено:**
- `Company` += `selected_metrics` (JSON) — миграция `012_company_selected_metrics`.
- `metric_catalog.describe_company()` — единая точка формирования профиля компании для AI.
- AI-слой (`insight_service`, `plan_generation_service`) получает контекст компании.
- Новые фронт-компоненты: `CompanyConfigDialog`, чекбоксы метрик в онбординге.
- Подписи индустрий/бизнес-моделей в списке компаний берутся из каталога (устранён рассинхрон).

**Архитектурные проблемы (обнаружены, не блокируют):**
- Каталог метрик data-driven (без `if industry == ...`), расширяемый — требование выполнено.
- Рекомендательный endpoint `/recommendations/get` — **автономный анализатор** (пользователь вводит
  метрики вручную, без привязки к компании), поэтому остаётся SaaS-ориентированным по дизайну.
  Контекст компании подставляется только в company-scoped сценарии (инсайты + генерация плана).
- `selected_metrics` — список ключей фиксированного словаря `Metric` (5 входных колонок). Это
  осознанное решение: не вводится полиморфная схема метрик (см. guardrail плана).

## 3. Database

- **БД:** PostgreSQL 15 (production/Docker), SQLite (локальная разработка/тесты).
- **Где физически:** Docker named-volume `postgres_data` на единственном сервере
  (`/var/lib/docker/volumes/<project>_postgres_data/_data`). БД доступна только по внутренней
  Docker-сети (порт наружу не проброшен).
- **Migrations:** Alembic, 12 миграций, head = `012_company_selected_metrics`. Круг
  `upgrade head` → `downgrade base` → `upgrade head` проходит на чистой SQLite.
- **Persistence:** есть — named-volume `postgres_data`.
  - `docker compose down` / `up` → данные сохраняются (volume не удаляется).
  - `docker rm <container>` → данные сохраняются (volume отделён от контейнера).
  - Данные теряются только при `docker compose down -v`, `docker volume rm` или потере диска хоста.
- **Backup:** **отсутствуют** (в репозитории нет `pg_dump`/backup-скриптов). Единственная копия — volume
  на одном сервере. **Рекомендация (не реализовано, нужен sign-off):** sidecar/cron `pg_dump` в
  customer-owned хранилище либо `pg_dump` по расписанию на хосте.

Новая миграция: `012_company_selected_metrics` — `companies.selected_metrics JSON NULL`.

## 4. Onboarding

Мастер `CompanyOnboardingWizard` (4 шага), data-driven из каталога `GET /catalog`:

1. **Название + Местонахождение** — выбор региона (Россия/Казахстан/Глобальный рынок) с подсказкой
   ключевой ставки.
2. **Отрасль (Industry)** — 15 отраслей из каталога (SaaS, Fintech, E-commerce, Marketplace, EdTech,
   HealthTech, AI, Mobile App, FoodTech, Logistics, PropTech, Media, Hardware, Biotech, CleanTech, Другое).
3. **Бизнес-модель** — 6 моделей (Подписка, Маркетплейс, Онлайн-ритейл, Финансовые сервисы,
   Мобильное приложение, Сервисы), **фильтруются по выбранной отрасли**.
4. **Рекомендуемые метрики** — чекбоксы (по умолчанию отмечены все рекомендованные), каждая с
   подписью и обоснованием «почему»; + валовая маржа. Выбор сохраняется в `selected_metrics`.

Рекомендации не являются жёстким ограничением — пользователь может снять/отметить метрики, а позже
изменить набор через «Настройки компании».

## 5. Metrics

- **Валовая маржа (Gross Margin, %)** — переработан UX: единый number-input с суффиксом «%» и кнопкой
  «Сохранить» в шапке вкладки «Метрики». Спиннеры скрыты (`appearance:textfield`), точность 0.5%
  сохранена (`step="0.5"`). Поле хранится на `company.gross_margin` (0..1). Отдельный блок обоснован
  семантически: это параметр компании (не помесячная метрика).
- **Исторический факт** — подтверждено, что ограничения «только прошлый месяц» в коде не было:
  `MonthPicker` без min/max, `MetricUpsert.period: date` без валидации периода. Ввод задним числом за
  1/3/6/12 месяцев работает (регресс-тест). Автологика текущего/предыдущего месяца не затронута.
- **Удаление** — `DELETE /companies/{id}/metrics/{metric_id}` + `ConfirmDialog` на фронте, реальное
  удаление на бэке, инвалидация React Query.

## 10. AI — статус функций

Провайдеры: **DeepSeek** (OpenAI-совместимый, `deepseek-chat`) и **GigaChat** (Сбер). Выбор через
`AI_PROVIDER`. При отсутствии ключа или ошибке провайдера — **детерминированный demo-фолбэк**
(правила, не нейросеть), который явно помечается `provider="demo"` и показывается в UI бейджем
«демо-режим». AI-слой отделён от бизнес-логики (`AIService.complete` — единая точка).

| AI Feature | Status | Model | Provider | Real API | Mock/Demo | Fixed |
| ---------- | ------ | ----- | -------- | -------- | --------- | ----- |
| Рекомендации (`/recommendations/get`) | REAL (автономный анализатор) | deepseek-chat | DeepSeek | Да (при ключе) | детерминированный фолбэк | — |
| Генерация плана (`/generate-plan`) | REAL + контекст компании | deepseek-chat | DeepSeek | Да | демо-план (+5%/мес) | ✅ контекст добавлен |
| AI-инсайты (11 сценариев) | REAL + контекст компании | deepseek-chat | DeepSeek | Да | детерминированный текст | ✅ контекст добавлен |
| Прогноз (Prophet) | LOCAL (не AI-вызов) | — | — | Нет | нет (детерминированный) | — |

**Пояснения к колонке «Real API»:** в текущем окружении `AI_PROVIDER=deepseek` и `DEEPSEEK_API_KEY`
задан в `backend/.env`, т.е. вызовы реально идут в DeepSeek. Валидность самого ключа на внешней
стороне в рамках этого аудита не проверялась (чтобы не совершать платные/внешние вызовы). При любом
сбое система честно падает в demo и показывает источник в UI — demo-плашка не скрывается.

**Контекст компании (пункт 18):** в промпты инсайтов и генерации плана теперь подставляется профиль
`metric_catalog.describe_company()`: отрасль, бизнес-модель, география, отслеживаемые метрики.
SaaS-специфичный текст заменён на нейтральный с инструкцией учитывать тип бизнеса
(MRR/churn/LTV/CAC для SaaS, GMV/комиссия/покупатели-продавцы для маркетплейса и т.д.).

**Что осталось SaaS-ориентированным (осознанно):** автономный анализатор рекомендаций
(`/recommendations/get`) не привязан к компании — пользователь вводит метрики вручную
(MRR/CAC/LTV/churn/ARPU/runway/stage), поэтому его промпт остаётся unit-economics-ориентированным.
Это отдельная функция, а не company-scoped сценарий.

## 11. Security — какие данные покидают инфраструктуру

- **Внешние вызовы приложения** (для self-hosted инстанса): только DeepSeek/GigaChat
  (агрегированные метрики/история фактов в промптах) и Let's Encrypt (TLS). Внешних БД нет.
- **Что уходит в AI:** рекомендации — агрегат `mrr/cac/ltv/churn/arpu/runway/stage`; план — история
  фактов `revenue/new_units/arpu/marketing_spend/retention_rate`; инсайты — JSON агрегатов модулей.
  **Не** уходят сырые данные БД целиком.
- **Что остаётся в БД:** все финансовые показатели, метрики, бюджеты, когорты, прогнозы, исторические
  данные. AI — отдельный слой, бизнес-данные не хранит (кэш ответов — в `ai_cache`, скоуп по `user_id`).
- **Self-hosted AI в будущем:** `AIService` — единственная точка; замена провайдера = новая реализация
  `_chat_*`/конфиг без изменения бизнес-логики. Возможна.
- **Утечка секретов:** исправлена ранее — `backend/.dockerignore` исключает `.env`/`*.db` из образа.
  Prod-секреты — в GitHub Secrets.

## 12. Deployment на инфраструктуре клиента

**Да, архитектурно возможно.** Весь стек (Nginx+React, FastAPI, Postgres) — docker-compose на одном
хосте; БД — локальный контейнер; `DATABASE_URL` — единственная точка подключения (можно подставить
customer-provided Postgres). Внешние зависимости: образы из ghcr.io (заменяемы локальной сборкой из
исходников), Let's Encrypt, AI-провайдеры (опционально `AI_PROVIDER=demo` — полностью автономно).

Минимальный план перехода: `docker compose -f docker-compose.prod.yml up -d --build` на сервере фонда →
переопределить `DATABASE_URL` на их Postgres при необходимости → добавить `pg_dump`-backup (не сделан).
